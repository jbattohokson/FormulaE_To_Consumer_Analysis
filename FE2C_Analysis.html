Summary

Formula E races run under a hard energy cap, so every race is effectively a battery management test. I wanted to know whether that racing work could tell California EV buyers something useful: does a bigger pack (energy density) or better regen (recovery efficiency) matter more where they drive?

The answer needs data that doesn't exist publicly, so I built the system first. It has a SQLite star schema for race and registration data, a ChromaDB store of technical documentation, and a Claude agent with 8 custom tools that answers questions across both. Twelve data quality checks run on every load, and all twelve pass. They include two added in the October 2026 audit, after the old simulation was found giving drivers in the same race different lap counts and ranking DNFs ahead of finishers while every check still passed.

Race outcomes are generated from a seeded simulation so results are reproducible, and the CA DMV feed currently returns a 2018 snapshot. The pipeline is built so real stint data can replace the simulated layer without changing anything downstream.

System Architecture

Three-layer agentic pipeline

Layer 1 · Structured Data

SQLite star schema

Fact table of race stints with dimensions for battery generation, track, manufacturer and weather. Weather comes from the Open-Meteo API, one call per track and race date, skipping pairs already loaded so reruns are idempotent.

Layer 2 · Semantic Search

ChromaDB vector store

Formula E technical documentation, FIA regulations and Lucid engineering material embedded and indexed, so the agent can pull qualitative context alongside the numbers.

Layer 3 · Agent

Claude tool-use agent

8 custom tools for circuit efficiency scoring, Delta-E calculation, regen opportunity indexing, cold-start circuit prediction, CA market simulation and county-level recommendations. Answers multi-step questions against both layers.

Design choices

Simulated race records use a fixed random seed per season so every run produces the same data. Every simulated row carries data_source = documented_outcomes_estimated_telemetry, so provenance is always queryable. CA registrations try the live DMV endpoint first and fall back to a reproducible synthetic set if it fails.

Metric Design

How efficiency is defined in the framework

M1Delta-E: efficient battery management vs. expensive position gains

Delta-E is a stint's energy-cost proxy (1 / EER proxy, where EER = race distance / (average lap x lap-time variance)) minus that race's average. A negative score means a driver used less energy than the field in that race. A positive score means more.

M2FE2C Efficiency Score: comparing across battery generations

FE2C Efficiency Score = 70% x EER proxy + 30% x average lap velocity, each min-max normalized within its battery generation, then scaled 0 to 100. The October 2026 audit found the old formula was inverted: it divided distance by the EER proxy, which rewarded slow, erratic stints as the most efficient. A test now plants a more efficient team in synthetic data and checks that it ranks first.

Assumption

Normalizing Gen 2 against Gen 3 requires assumptions about how capacity differences map to comparable efficiency. Those assumptions are documented in the pipeline code and its data quality checks.

Limitations

What this project does not claim

LThree things to keep in mind

1. Race outputs come from simulated data. Efficiency scores and Delta-E values describe the simulated dataset. They show that the pipeline and metrics work, not how real teams performed.

2. The Lucid technology-transfer angle is a case study premise. Lucid's Atieva division built the spec battery for every Gen 2 car (2018-19 to 2021-22), and since 2023 Lucid has supplied the Gen 3 front drive unit, also to every team. Because every team ran Lucid hardware, there's no Lucid vs. non-Lucid comparison inside Formula E; the pipeline tracks Mahindra as a focus team only. What actually transferred to Lucid's road cars, and when, isn't public.

3. The California recommendation is a weighted framework, not a demand model. It uses registration density and environmental factors. Validating it would need real buyer data from each region.

Next step

Replace the simulated stint layer with real race results and timing data, keeping the same schema, so the data quality checks and agent tools run unchanged on real inputs.
